# 官方通道实现与验证边界

## 已直接核对的来源

用户提供的 `tencent-connect-qqbot-connector-1.2.0.tgz`：

- `package/README.md`：`qrConnect`、`startQrConnect`，返回凭据数组，二维码过期刷新及取消。
- `package/dist/esm/qr-connect.js`：回调返回 `appId`、`appSecret`，实现额外返回可选 `userOpenid`。公开类型不承诺这个字段，因此接入有缺失兜底，不把首次陌生来信自动授权。
- `package/dist/esm/qqbot-session.js`：SDK 访问 `q.qq.com/lite/create_bind_task`、`poll_bind_result`，使用随机密钥和 AES-GCM 解密应用密钥；本项目直接使用包的公开接口，不复制这一协议。
- 包只导出扫码绑定接口，不提供消息网关或发送 API。

## 消息通道采用的协议及待核实项

独立适配器实现 `bots.qq.com/app/getAppAccessToken`、`api.sgroup.qq.com/gateway`、WebSocket Identify/Resume/Heartbeat，以及 `/v2/users/{openid}/messages`、`/v2/groups/{group_openid}/messages`。

这些消息接口不是扫码 SDK 提供或验证的契约。本次环境无法访问外部文档或服务，消息通道按 QQ 机器人 v2 协议实现，但仍须在实际账号上核实以下条件：

1. 扫码所得应用是否开放 WebSocket 接入和 `GROUP_AND_C2C_EVENT` 事件权限。
2. 私聊和群 @事件中的用户/群 OpenID 及内容格式。
3. 鉴权头、被动回复 `msg_id` / `msg_seq` 在当前平台版本中的行为。
4. 应用允许的被动回复时间、数量、内容长度及主动消息权限。代码使用 4 分钟/5 段的保守本地上限，不宣称这是平台保证。
5. 当前账号真实扫码、机器人添加及消息收发成功。

## 本地验证方式

`npm test` 使用真实业务代码与可注入的 HTTP、WebSocket、扫码 SDK 回调替身。覆盖 Token 缓存及刷新、401/429/500、不自动重放发送 POST、网关心跳/重连/Resume、权限拒绝、OpenID 白名单、应用隔离、回复窗口/次数、长文本分段，以及官方消息到工单结果保存的完整流程。

`test/connector-sdk.test.js` 还直接调用下载包中的真实 `startQrConnect`，用模拟 HTTPS 响应验证终端二维码、AES-GCM 凭据解密和回调，确认不会输出 AppSecret。

结果补取测试模拟任务执行期间回复窗口过期、需求确认耗尽回复额度两种情形，检查任务保持待验收、结果全文持久化、新消息 `/result` 使用新的 `msg_id` 和 `msg_seq=1` 逐页取回、模型只运行一次。另覆盖长结果仅推送首页、UTF-8 页大小、跨聊天/工单隔离、翻页固定回复编号、旧数据库重启取回。不会放宽被动回复限制或自动启用主动推送。

这验证了本地逻辑和请求构造，不等同于远端协议或账号权限已通过实测。没有向真实联系人发送消息，也没有调用 Claude 模型。

验证设计参考 `postman:api-simulation` 的失败注入和证据边界。由于当前环境网络及本地监听限制，本次没有运行 Postman HTTP simulation server；使用项目已有的依赖注入测试方式，不把替身响应当成平台事实。

## 联调顺序

1. Node 24 下运行 `npm run login`，用户手机扫码确认，检查终端仅显示 AppID。
2. 填写工作目录和用户 OpenID，运行 `npm run check`、`npm start`。
3. 用户主动发 `/help`、一个只读需求，再验证 `/status` 和 `/history`。
4. 授权一个群 OpenID，由白名单成员 @机器人，验证群审批及隔离。
5. 确认应用具备主动消息权限后才开启 `QQBOT_ALLOW_PROACTIVE`，再实测长任务和定时推送。

联调前不要覆盖参考项目或其他应用的数据库。每个应用默认使用独立 SQLite 文件。


## 图片扩展的验证边界

接收端读取官方事件的 `attachments`（`content_type` / `filename`、`url`、`size`），OneBot 读取 `image` 消息段。通过白名单后才下载 QQ CDN 图片，禁止跳转到其他域名，控制响应流的实际大小；图片 base64 与 MIME 随消息存入 SQLite，Claude 使用 SDK 的 `SDKUserMessage` 图片块接收。

发图采用 `/v2/users/{openid}/files` 或 `/v2/groups/{group_openid}/files`，请求 `file_type=1`、`file_data=<base64>`、`srv_send_msg=false`；收到 `file_info` 后，再调用 messages 接口发送 `msg_type=7` 的 media。该接口字段与图片上传权限尚未在真实账号上实测；本地替身测试验证的是请求构造与失败处理。OneBot 使用 `image` 段的 `base64://` 文件内容发送。

新增测试覆盖纯图片与图文消息、白名单、CDN 跳转、超限及伪装文件、真实路径/符号链接围栏、MCP 发图工具、取消与迟到调用、Claude SDK 图片块、工单排队、旧数据库迁移、重启恢复、官方上传和发送两阶段回执、文本/图片共享序号、OneBot 图片发送及定时任务发图目标隔离。

真实联调请由用户在 QQ 发一张小 PNG 并附“解释这张图”，然后要求“生成一个测试图并发回来”。检查图像分析结果、QQ 图片实际显示，以及上传/发送失败能否收到明确说明。桥接不内置图像生成模型或浏览器。

## 普通文件与折叠摘要的验证边界

普通文件工具和 `/file` 已接入。本地测试覆盖文件名与 base64 校验、10 MiB 上限、真实路径围栏、MCP 工具权限、取消、固定聊天目标、迟到回调，以及官方上传/消息两阶段回执和 OneBot 上传失败。

官方实现尝试 `/v2/users|groups/{id}/files` 的 `file_type=4`、`file_data`、`file_name`，随后发送 `msg_type=7`。这些普通文件字段、平台可用性和应用权限未经真实账号验证，平台可能完全不支持此类别；模拟成功响应只验证本地控制流，不是可用性证据。OneBot 使用 `upload_private_file` / `upload_group_file` 加 `base64://`，需要兼容的扩展实现；成功只表示接口接受，不保证收件人已看到文件。不自动改传公网托管，不自动重放超时发送。

`/verbose on` 记录 SDK 明确返回的思考摘要和工具名称，默认仅展示文字入口，通过 `/verbose show` 查看，没有实现 QQ 原生可点击折叠。测试覆盖关闭默认值、聊天隔离、重启持久化、执行中切换、停止后迟到事件、隐藏块/签名排除、大小限制和分页；不需要调用模型。真实模型是否返回 `thinking` 取决于模型和 SDK，未返回时不伪造摘要；本次未验证真实 QQ 客户端展示效果。
